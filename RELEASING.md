# Releasing agent-cli-spec

Releases go through the shared maelys-release socle, at the version the
`uses:` lines of `.github/workflows/release.yml` and `ci.yml` pin. The
workflow `.github/workflows/release.yml` and `scripts/checkout-dependency.sh`
are generated by its `maelys-release adopt` from `VERSION`,
`dependencies/*.pin`, `dependencies/packages` and `packaging/homebrew/*.rb.in`.

1. On `main`: `VERSION` = `X.Y.Z`, dated `CHANGELOG.md` entry, generated
   documentation regenerated, `make check` green on the exact commit.
2. Merge through a pull request with green CI (`ci.yml` runs the socle's
   `check-product.yml` on the three release targets). Before a first
   release or after a packaging change, `maelys-release rehearse . linux-arm64`
   replays the Linux build job in Docker.
3. `maelys-release preflight .` from any maelys-release checkout (it runs as
   the version the product pins): signing configuration, previous tag, free
   `vX.Y.Z`, `release` environment.
4. `git tag -s vX.Y.Z -m "agent-cli-spec X.Y.Z" && git push origin vX.Y.Z`, or
   `maelys-release cut . X.Y.Z --tag --apply`, which signs the tag on the
   merge commit the checks ran on.
5. The workflow verifies the signed annotated tag, clones the pinned
   dependencies, installs the declared packages, builds the packages on
   Linux x86_64, Linux arm64 and macOS arm64, attests their provenance,
   publishes the GitHub release. Homebrew jobs apply only when a product
   declares a formula; this repository does not.
6. Verify: `gh release view vX.Y.Z`, `gh attestation verify ASSET --repo
   OWNER/REPO --signer-repo maelys-dev/maelys-release` (the provenance is
   signed by the socle's reusable workflow, so `--repo` alone fails).
   Extract the archive and verify that it contains both `LICENSE` and
   `LICENSE-SPEC`. This repository currently publishes archives only; it
   declares no Homebrew formula and has no tap publication job.

Upgrade the socle with `maelys-release adopt DIR --apply` from a maelys-release
checkout at the wanted tag; `maelys-release check DIR` reports drift with exit 2.

## Before a tag that changes the contract

A change of the contract is a change of five things, in the same pull
request, and a tag is cut once another implementation has run it:

1. the sentence, in `spec/agent-cli.md`, with its reason;
2. the schema, where the rule has a shape;
3. the fixture, which does what the sentence says;
4. the kit, which checks it on lines that are safe to run, and says in
   `scope.notChecked` what it does not check;
5. a defect of the fixture (`CONFORMANT_BREAK`) that proves the check fails,
   listed in `tests/test_kit.py`.

Then, before any tag:

- `make check`, and the generated lines of `tests/test_invariants.py` with an
  empty list of known gaps;
- `make siblings-check` on a built checkout of maelys-cli: the kit and the
  generated lines on its programs. A failure there is a defect of that
  implementation, a defect of this repository, or a point the contract
  leaves open, and it is classified before the tag, not after;
- read every sentence of the text that uses the same key word as the new
  one. 2.13.1 was a sentence that contradicted its neighbour;
- no tag while a point is "left open, to be asked": ask first. 2.12.0
  reversed two choices of 2.11.0 the day after;
- the changelog entry says in bold what makes a program fail from this
  version, and the table at its top gains a row.

With maelys-cli the exchange is on commits: each side names the commit to
try, runs the other's unreleased work, and sends everything it found in one
message. One tag is cut on each side when both have agreed on a named pair
of commits; the tagged tree is the agreed one, to `VERSION` and the date.

## Protecting the default branch

`main` is protected by a repository **ruleset**. The contexts it requires are
derived, never typed: `maelys-release protect .` computes them from the
socle's check job, and `protect . --apply` writes them into the ruleset.

After an adoption that renames a check, the order is **adopt, merge, then
`protect . --apply`**. The socle keeps reporting the former names as aliases
until the protection moves, so the adoption's own pull request passes and the
branch never requires less; `--apply` replaces each alias by its leg in one
write, and refuses before the adoption is merged. Never narrow the ruleset to
get an adoption through.

## Replaying a tag

`release.yml` accepts a `workflow_dispatch` whose `tag` input names an
existing signed tag, and replays the whole release for it, the formula
included where a product declares one. Adopt a corrected socle on the default
branch first, then `gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z`.
`--ref` names the tag: the `release` environment accepts tags `v*` alone, so a
run started from the default branch is refused at `publish`. A replay runs the
socle that tag pinned; when the socle is at fault, the remedy is a new patch
release carrying the corrected pin. A tag is never
moved or recreated.
